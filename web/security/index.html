Security

Read this before you trust it.

What went wrong in our earlier funds, what changed, what the chain proves and what you still have to trust. Plinth has only run on NEAR testnet, with test tokens.

Known issue · releases 0.1 and 0.2

The bug in our earlier funds.

What happened

Every fund created before release 0.3 has it, including the earlier funds in the app. Those releases counted a token transfer that was about to bounce back as if the fund owned it. Anyone could use that to take more than their share, or to mark a trade settled before anything was delivered. A proof of concept, commit 0094ff0, showed both. Two earlier reviews did not find it.

What we did

Those funds have no keys, so they cannot be fixed. They hold test tokens only. The app keeps them in a separate group with a warning on each, and the verifier will not call them safe. Release 0.3 removes the cause; tests in the repository replay both tricks and show they do nothing on 0.3.

What release 0.3 changed

A fund counts a token only when it is handed it.

Release 0.3 never trusts a balance it reads. Tokens count only when they arrive with a message the fund recognises, or when one of the fund's own calls brings them back.

What arrivesHow the fund counts it
A deposit to joinCounted as it arrives, during the join window.
The result of a trade1Click hands it to the fund with this trade's tag, and the trade settles on the spot.

Proven and trusted

What the chain proves, and what it cannot.

Checked from the chain

The verifier checks each of these in your browser.

  • The fund's account has no keys.
  • It runs the one published copy of a listed release, fixed by its fingerprint.
  • The code has no instruction that can deploy code, change keys, stake or delete the account.
  • Refunds go to a keyless account that can only pass them on to this fund.
  • The fund's own rules, as the contract reports them.

Still trusted

These the contract checks as far as it can, but cannot prove.

  • 1Click delivers the result of a trade or refunds it. The contract checks the signed quote; it cannot force delivery.
  • 1Click's dollar prices, which the cost cap uses.
  • 1Click's signing key. If it changes, the fund can no longer trade; leaving still works.
  • For a fund with no manager: OutLayer, which runs its program. Its answer is checked like any manager's proposal.
  • That 1Click's hand-over with a message works on mainnet. It is documented, and untested here.

Limits

Every known limit, in plain words.

  • No fixes, ever. A keyless contract cannot be upgraded. A bug is permanent; the issue above is the proof. Funds should start small.
  • Refunds go through a separate account. A refund from 1Click arrives as a plain transfer that nobody can see land, so it goes to a second keyless account that holds nothing else and can only pass tokens on to its fund. The fund counts tokens only when it is handed them; it reads no balance anywhere. What is left: a refund that 1Click sends anywhere else, or tokens anyone sends straight to a fund with a plain transfer, are never counted.
  • Delivery with a message is untested on mainnet. Release 0.3 needs 1Click to hand the output to the fund together with a short message. NEAR Intents documents this and marks it experimental. No Plinth fund has received a real 1Click delivery this way. If 1Click gave the hand-over too little gas, the output would go back to 1Click and the fund would not get it.
  • No manager does not mean nothing to trust. A fund without a manager lets anyone ask a fixed program for a proposal. The program runs at OutLayer, and the fund cannot check on chain that it ran inside a secure enclave. A forged answer can do what a manager could and no more: propose a trade inside the rules. On testnet the program signs its own stand-in quotes with a key anyone can read. If OutLayer refuses a run, the small NEAR attached stays with the fund. Exits never depend on any of this.
  • 1Click is trusted to deliver or refund. The contract checks the signed quote; it cannot force delivery.
  • Prices are 1Click's. The cost cap uses the dollar values in the signed quote, so it bounds cost against 1Click's own valuation, not against the whole market.
  • One signing key. 1Click's key is fixed in the fund. If it changes, the fund can no longer trade, but exits still work.
  • Testnet stand-in. 1Click has no testnet, so the recorded runs use a test signer and a solver account in 1Click's place. The verifier labels it.
  • App fees are bounded, not blocked. 1Click does not sign its app-fee field, so a manager can take a fee inside a trade. The cost cap still bounds it. Each fund card shows the most this can cost in one day.
  • Only test tokens so far. The tests use a test token. No test here runs the real wNEAR or stNEAR code from mainnet, and Plinth has only run on testnet.
  • At most 4 tokens. So one exit can pay every token in a single transaction.
  • Exit waits for one trade. While a trade is in flight, exits wait up to 10 minutes. After that you can leave without your share of that one trade.
